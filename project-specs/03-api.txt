# 03-api.md

# Padrão de Integração com APIs

## Objetivo

Este documento define os padrões de integração entre a aplicação **Plano de Controle CQ** e os serviços externos, principalmente as APIs do **TOTVS Datasul**.

Seu objetivo é garantir que toda comunicação com sistemas externos siga uma arquitetura consistente, desacoplada e preparada para evolução futura.

As implementações realizadas por agentes de IA devem respeitar integralmente estas diretrizes.

---

# Arquitetura da Integração

Toda comunicação externa deve seguir obrigatoriamente o fluxo abaixo:

```text
Tela (Component)

↓

Facade (quando necessário)

↓

Service

↓

HttpClient

↓

API Datasul

↓

Service

↓

Model

↓

Tela
```

Os componentes da interface nunca devem acessar diretamente o `HttpClient`.

---

# Princípios Gerais

Toda integração deve ser:

* Assíncrona
* Desacoplada
* Tipada
* Reutilizável
* Testável

A lógica de comunicação nunca deve ficar na camada de apresentação.

---

# Organização dos Services

Cada funcionalidade deverá possuir seu próprio serviço.

Exemplo:

```text
services/

login.service.ts

equipes.service.ts

centro-trabalho.service.ts

reporte-operacoes.service.ts

reporte-paradas.service.ts

plano-controle.service.ts
```

Services genéricos somente quando houver real necessidade de reutilização.

---

# Padrão de Métodos

Os serviços devem possuir métodos claros e descritivos.

Exemplos:

```typescript
consultarEquipe()

salvarEquipe()

listarOperadores()

consultarCentroTrabalho()

consultarOrdens()

registrarParada()

registrarRefugo()

gerarPlanoControle()
```

Evitar nomes genéricos como:

```typescript
getData()

save()

request()

execute()
```

---

# Tipagem

Nunca utilizar objetos anônimos.

Toda requisição e resposta deverá possuir uma interface específica.

Exemplo:

```typescript
EquipeRequestDTO

EquipeResponseDTO

OperadorDTO

CentroTrabalhoDTO
```

---

# Models

Os dados retornados pela API nunca devem ser utilizados diretamente pela interface.

Sempre converter DTO para Model.

Fluxo esperado:

```text
API

↓

Response DTO

↓

Mapper

↓

Model

↓

Tela
```

---

# Mapeamento

Sempre utilizar funções específicas para conversão.

Exemplo:

```typescript
mapEquipeResponse()

mapOperador()

mapCentroTrabalho()
```

Nunca realizar transformações diretamente no componente.

---

# Tratamento de Erros

Toda chamada HTTP deve tratar:

* Timeout
* Erro de autenticação
* Erro de autorização
* Erro de validação
* Erro de comunicação
* Erro interno do servidor
* Resposta inesperada

Os erros devem ser convertidos em mensagens compreensíveis para o usuário.

Nunca exibir mensagens técnicas da API.

---

# Loading

Toda requisição deve possuir indicador visual.

Fluxo esperado:

```text
Usuário inicia ação

↓

Loading

↓

API

↓

Sucesso ou Erro

↓

Loading encerrado
```

---

# Retry

Quando apropriado, permitir nova tentativa após falha de comunicação.

Exemplo:

* perda de conexão
* timeout
* indisponibilidade temporária

---

# Cancelamento de Requisições

Sempre cancelar chamadas que não são mais necessárias.

Exemplos:

* troca de tela
* nova pesquisa
* fechamento de painel

Evitar múltiplas requisições concorrentes desnecessárias.

---

# Cache

Somente utilizar cache para informações pouco voláteis.

Exemplos:

* Centros de Trabalho
* Turnos
* Motivos de Parada
* Tipos de Inspeção

Nunca manter em cache informações transacionais sem estratégia definida.

---

# Segurança

Nunca armazenar:

* Senhas
* Tokens em texto puro
* Informações sensíveis

Toda autenticação deverá seguir a estratégia definida pelo backend.

---

# Validação

Antes de enviar qualquer requisição:

* validar campos obrigatórios
* validar formatos
* validar tipos
* impedir envio de dados inconsistentes

A validação deve ocorrer preferencialmente na interface, mas também deve ser considerada no backend.

---

# Estrutura dos DTOs

Exemplo:

```typescript
export interface EquipeResponseDTO {

    codigo: string;

    descricao: string;

    turno: string;

    operadores: OperadorDTO[];

}
```

---

# Estrutura dos Models

Exemplo:

```typescript
export interface Equipe {

    id: string;

    codigo: string;

    descricao: string;

    turno: string;

    operadores: Operador[];

}
```

Os Models representam a estrutura utilizada pela aplicação, independentemente do formato retornado pela API.

---

# Convenções HTTP

Preferencialmente utilizar:

* GET para consultas
* POST para inclusão
* PUT para atualização
* DELETE para remoção

Seguir sempre as convenções REST quando suportadas pela API do Datasul.

---

# Observables

Todas as chamadas HTTP devem retornar `Observable`.

Evitar conversões desnecessárias para Promise.

Utilizar operadores do RxJS quando necessário.

---

# Tratamento de Respostas

Toda resposta deve ser validada antes de ser utilizada.

Verificar:

* estrutura
* tipos
* campos obrigatórios
* valores nulos

Nunca assumir que a API retornará dados válidos.

---

# Logs

Registrar apenas informações úteis para depuração.

Nunca registrar:

* senha
* token
* dados sensíveis

---

# Integração com Datasul

A implementação deve considerar que:

* os endpoints poderão evoluir;
* novos campos poderão ser adicionados;
* novas funcionalidades poderão surgir.

Por esse motivo, o código deve ser desacoplado da estrutura exata da API.

---

# Simulação de APIs

Durante o desenvolvimento inicial é permitido utilizar mocks.

Os mocks devem possuir a mesma estrutura esperada da API real.

A substituição para os endpoints reais deve ocorrer apenas na camada de Services.

---

# Padrões para Agentes de IA

Ao implementar qualquer integração, o agente deve:

* Nunca utilizar `HttpClient` diretamente na tela.
* Criar interfaces para Request e Response.
* Criar Models separados.
* Criar métodos descritivos.
* Implementar tratamento de erros.
* Implementar loading.
* Utilizar tipagem forte.
* Preparar a estrutura para futura integração com o Datasul.
* Manter o código desacoplado da implementação específica da API.

---

# Checklist

Antes de concluir uma integração, verificar:

* Existe Service específico.
* Existe interface Request.
* Existe interface Response.
* Existe Model.
* Existe Mapper.
* Existe tratamento de erro.
* Existe loading.
* Existe validação.
* Não há uso de `any`.
* Não há chamadas HTTP na camada de apresentação.
* A implementação está preparada para integração com a API do Datasul.
