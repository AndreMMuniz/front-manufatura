# Geração de Roteiro

> Documento AI-First destinado aos agentes de código (Codex, BMAD, Claude Code e OpenCode).

---

# 1. Objetivo

A tela **Geração de Roteiro** é o ponto de entrada do módulo de **Inspeção de Processo**.

Sua responsabilidade é localizar uma Ordem de Produção, identificar o processo que será inspecionado e gerar o roteiro de inspeção que será utilizado pela próxima etapa do fluxo.

Esta tela não realiza inspeções.

Ela apenas prepara o contexto operacional necessário para que a tela **Inspeção de Processo** possa ser iniciada.

Todo o fluxo deve ser otimizado para utilização em tablets industriais, priorizando rapidez de operação, baixa quantidade de interações e suporte à leitura por código de barras.

---

# 2. Contexto de Negócio

Antes que uma inspeção de qualidade possa ser executada, é necessário identificar corretamente:

* Ordem de Produção
* OP
* Split
* Processo
* Operação
* Item produzido

Essas informações são obtidas através da integração com o ERP Datasul.

Após localizar a ordem, o sistema exibe seus dados para conferência e permite que o operador gere o roteiro de inspeção correspondente.

O roteiro gerado servirá como base para toda a execução da inspeção de processo.

Elementos:

* Logo Cortag
* Título:

  * **Inspeção Processo**
* Subtítulo:

  * **Geração de Roteiro**

O cabeçalho possui apenas função de identificação da funcionalidade.

---

## 5.2 Área de Pesquisa

Responsável por localizar a Ordem de Produção.

Componentes:

### Input Ordem

Tipo:

* PO Input

Função:

Permite informar manualmente o número da Ordem de Produção.

---

### Input OP

Tipo:

* PO Input

Função:

Permite informar a OP correspondente à ordem consultada.

---

### Input Split

Tipo:

* PO Input

Função:

Permite informar o Split da Ordem de Produção.

---

### Scanner

Tipo:

* Botão de ação

Ícone:

Câmera.

Função:

Permite utilizar a câmera do tablet para leitura de:

* Código de barras
* QR Code
* Outro padrão definido pelo ERP

Após uma leitura válida, os campos necessários devem ser preenchidos automaticamente.

---

## 5.3 Painel de Informações

Após localizar a Ordem, o sistema apresenta um painel somente leitura contendo as informações retornadas pelo Datasul.

Campos exibidos:

* Roteiro
* Processo
* Ordem Atual
* Operação
* Split
* Item
* Descrição

Características:

* Não editável
* Atualização automática após consulta
* Deve utilizar tipografia monoespaçada ou alinhamento consistente para facilitar a leitura em ambiente industrial

---

## 5.4 Configuração da Inspeção

Componente:

Checkbox.

Descrição:

**Movimenta saldo**

Função:

Determina se a geração do roteiro deverá considerar a movimentação de saldo conforme as regras de negócio definidas pelo ERP.

O significado operacional dessa opção será detalhado na seção de regras de negócio.

---

## 5.5 Área de Ações

### Botão Principal

**Gerar Roteiro**

Responsabilidades:

* Validar os dados informados
* Garantir que a Ordem foi localizada
* Gerar o roteiro de inspeção
* Preparar o contexto da próxima tela
* Navegar para **Inspeção de Processo**

---

### Botão Voltar

Retorna para a tela **Centro de Trabalho**.

Nenhum dado deve ser persistido.

---

### Botão Sair

Cancela completamente o fluxo de inspeção.

Retorna ao menu principal da aplicação conforme definido em `02-fluxo-geral.md`.

# 6. Layout para Tablets

Esta tela foi projetada exclusivamente para operação em tablets industriais.

Diretrizes:

* Layout vertical (Portrait)
* Componentes com área mínima de toque conforme definido no Design System
* Campos distribuídos em coluna única
* Botão principal destacado na região inferior direita
* Navegação inferior fixa
* Espaçamento suficiente para operação com luvas industriais, quando aplicável
* Não utilizar barras de rolagem horizontais
* Evitar sobreposição de elementos durante abertura do teclado virtual

Todo o comportamento responsivo deve seguir as diretrizes estabelecidas em `05-padroes-ui.md`.

# 11. Regras de Negócio

## RN-01

Não permitir gerar roteiro sem uma Ordem válida.

---

## RN-02

Os dados exibidos devem ser provenientes exclusivamente do Datasul.

Não é permitido edição manual.

---

## RN-03

O painel de informações é somente leitura.

---

## RN-04

A geração do roteiro depende da validação completa da Ordem de Produção.

---

## RN-05

A navegação para **Inspeção de Processo** somente poderá ocorrer após confirmação de sucesso da geração do roteiro.

---

## RN-06

A opção **Movimenta saldo** deve ser enviada ao backend como parâmetro da geração do roteiro.

A lógica de movimentação será executada exclusivamente pelo backend.

---

## RN-07

Caso o ERP informe inconsistências na Ordem, o fluxo deve ser interrompido e a mensagem retornada deve ser apresentada ao operador.

---

# 12. Regras de UX

* Priorizar operação por toque.
* Evitar múltiplos cliques durante consultas.
* Nunca apagar informações preenchidas após erro de comunicação.
* O foco inicial deve permanecer no campo **Ordem**.
* Após leitura via scanner, o foco deve ser removido do teclado virtual para ampliar a área útil da tela.
* O botão **Gerar Roteiro** deve possuir maior destaque visual que as ações secundárias.
* O painel de informações deve ser atualizado instantaneamente após o retorno da API, sem necessidade de ação adicional do usuário.
* Sempre apresentar feedback visual durante operações assíncronas.
* As mensagens de erro devem ser claras, objetivas e orientadas à ação, evitando códigos técnicos ou mensagens provenientes diretamente da API.

# 13.1 Consulta da Ordem de Produção

Objetivo:

Localizar uma Ordem de Produção válida e retornar todas as informações necessárias para geração do roteiro.

Dados enviados:

```typescript
{
  ordem: string;
  op: string;
  split: string;
}
```

Resposta esperada:

```typescript
{
  roteiro: string;
  processo: string;
  ordemAtual: string;
  operacao: string;
  split: string;
  item: string;
  descricao: string;
}
```

---

# 13.2 Geração do Roteiro

Objetivo:

Solicitar ao ERP a criação do roteiro de inspeção.

Dados enviados:

```typescript
{
  ordem: string;
  op: string;
  split: string;
  movimentaSaldo: boolean;
}
```

Resposta esperada:

```typescript
{
  roteiroId: string;
  status: string;
}
```

Após retorno com sucesso, a aplicação deverá navegar automaticamente para a tela **Inspeção de Processo**.

---

# 13.3 Tratamento de Erros

As respostas de erro deverão ser tratadas pela camada de Service.

A interface não deve interpretar códigos do ERP.

Responsabilidades do Service:

* traduzir mensagens técnicas
* padronizar erros
* registrar logs
* disponibilizar mensagens amigáveis para a UI

# 18. Gerenciamento de Estado

A tela possui baixo nível de complexidade e não necessita de um Store global.

O estado poderá ser mantido localmente utilizando:

* Angular Signals (preferencialmente)
* ou RxJS, conforme padrão arquitetural do projeto

Estados controlados:

* Ordem informada
* OP
* Split
* Dados da Ordem
* Loading
* Movimenta saldo
* Resultado da consulta
* Resultado da geração do roteiro

Ao navegar para **Inspeção de Processo**, os dados necessários deverão ser transferidos por meio do mecanismo de navegação definido na arquitetura da aplicação (Router State, serviço compartilhado ou outra estratégia padronizada no projeto), evitando consultas redundantes ao backend sempre que possível.

# 22. Cenários de Exceção

## Falha de comunicação

O sistema deve:

* manter os campos preenchidos;
* informar a indisponibilidade do serviço;
* permitir nova tentativa sem reiniciar a tela.

---

## Ordem inválida

Caso a Ordem esteja inconsistente:

* impedir geração do roteiro;
* apresentar mensagem retornada pelo Service;
* manter o usuário na tela.

---

## Dados incompletos

Caso algum campo obrigatório não seja informado:

* impedir consulta ou geração do roteiro;
* destacar visualmente os campos obrigatórios;
* posicionar o foco no primeiro campo inválido.

---

## Múltiplos acionamentos

Durante qualquer operação assíncrona:

* bloquear novos cliques;
* impedir múltiplas requisições simultâneas.

---
