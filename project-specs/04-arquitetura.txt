# 04-arquitetura.md

# Arquitetura da Aplicação

## Objetivo

Este documento define a arquitetura técnica obrigatória do projeto **Plano de Controle CQ - Cortag**.

Todas as implementações realizadas por agentes de IA (Codex, BMAD, Claude Code, OpenCode ou similares) devem seguir rigorosamente este documento. Nenhum componente, serviço ou tela deve ser desenvolvido ignorando estas diretrizes.

---

# Stack Tecnológica

## Framework

* Angular (versão mais recente estável)
* Standalone Components
* TypeScript Strict Mode

## Biblioteca de Componentes

* PO-UI

Todos os componentes visuais devem utilizar componentes nativos do PO-UI sempre que houver equivalência.

Evitar componentes HTML puros quando existir um componente PO-UI correspondente.

---

# Arquitetura da Aplicação

A aplicação deve seguir uma arquitetura baseada em funcionalidades (Feature First).

Cada funcionalidade possui seu próprio conjunto de componentes, serviços, modelos e interfaces.

Exemplo:

```text
features/

    equipes/
        pages/
        components/
        services/
        models/
        interfaces/

    centro-trabalho/
        ...

    reporte-operacoes/
        ...
```

---

# Organização dos Arquivos

Cada tela deverá possuir no mínimo:

```text
feature/

    page/

        equipes.page.ts
        equipes.page.html
        equipes.page.scss

    services/

        equipes.service.ts

    models/

        equipe.model.ts

    interfaces/

        equipe.interface.ts

    components/

        operador-list.component
        alterar-equipe-panel.component
```

---

# Componentização

Componentes devem possuir responsabilidade única.

Não criar componentes com múltiplas responsabilidades.

Sempre que um trecho da interface puder ser reutilizado, ele deverá ser extraído para um componente independente.

Exemplos:

* Lista de Operadores
* Cabeçalho
* Painel Lateral
* Cards de Informação
* Loading
* Mensagens

---

# Separação de Responsabilidades

## Component

Responsável apenas por:

* interação do usuário
* renderização
* binding
* eventos

Nunca implementar regras de negócio diretamente no componente.

---

## Service

Responsável por:

* chamadas HTTP
* integração Datasul
* transformação de DTO
* tratamento de erros
* cache quando necessário

Toda comunicação externa deve passar por Services.

---

## Models

Representam entidades internas da aplicação.

Exemplo:

* Equipe
* Operador
* CentroTrabalho

---

## Interfaces

Representam contratos.

Utilizar interfaces para:

* DTO da API
* retorno de consultas
* requests
* responses

---

# Gerenciamento de Estado

Preferencialmente utilizar:

* Angular Signals

Caso necessário:

* RxJS

Evitar Subject desnecessário.

---

# Change Detection

Utilizar:

```text
ChangeDetectionStrategy.OnPush
```

em todos os componentes.

---

# Injeção de Dependência

Utilizar o padrão oficial do Angular.

Não instanciar classes manualmente.

---

# HTTP

Toda chamada HTTP deve ficar em Services.

Nunca utilizar HttpClient diretamente dentro de Components.

---

# DTO

Nunca utilizar diretamente o objeto retornado pela API.

Criar DTO específico.

Exemplo:

```text
EquipeResponseDTO

↓

EquipeModel

↓

Tela
```

---

# Tratamento de Erros

Todo Service deverá tratar:

* erro de comunicação
* timeout
* erro de autenticação
* erro de validação
* erro inesperado

Sempre retornar mensagens amigáveis para a interface.

---

# Loading

Toda chamada assíncrona deverá possuir indicador visual de carregamento.

Nunca deixar a interface aparentemente travada.

---

# Navegação

Utilizar Angular Router.

Nunca realizar navegação manipulando window.location.

---

# Estrutura dos Componentes

Cada componente deverá possuir:

* HTML
* SCSS
* TS

Nunca utilizar templates inline.

---

# Estilos

Utilizar SCSS.

Não utilizar CSS inline.

Não utilizar atributos style.

---

# Organização do CSS

Priorizar:

* Flexbox
* Grid

Evitar posicionamentos absolutos desnecessários.

---

# Responsividade

A aplicação é otimizada para tablets industriais.

Resoluções prioritárias:

* 1280x800
* 1024x768
* 1366x768

A interface deve permanecer funcional em orientação horizontal.

---

# Performance

Evitar:

* loops desnecessários
* renderizações repetidas
* cálculos no template

Utilizar trackBy em listas.

---

# Tipagem

Nunca utilizar:

```typescript
any
```

Sempre criar interfaces ou tipos específicos.

---

# Código

Seguir Clean Code.

Nomes claros.

Métodos curtos.

Baixo acoplamento.

Alta coesão.

---

# Convenções

Classes:

```text
EquipeService
EquipeModel
EquipePage
OperadorComponent
```

Métodos:

```text
carregarEquipe()

salvarEquipe()

abrirPainelOperadores()

fecharPainel()

consultarOperadores()
```

Variáveis:

camelCase

Constantes:

UPPER_SNAKE_CASE

---

# Componentes PO-UI Permitidos

Priorizar:

* po-page-default
* po-toolbar
* po-button
* po-input
* po-select
* po-table
* po-modal
* po-page-slide
* po-loading
* po-notification
* po-checkbox
* po-switch
* po-divider

---

# Comunicação entre Componentes

Preferencialmente utilizar:

* @Input
* @Output
* Signals

Evitar comunicação indireta desnecessária.

---

# Testabilidade

Toda regra de negócio deve ser implementada em Services para facilitar testes unitários.

---

# Reutilização

Antes de criar um novo componente, verificar se já existe componente equivalente.

Duplicação de código não é permitida.

---

# Integração com Datasul

Toda integração deve ocorrer através de Services.

Os Components nunca devem conhecer detalhes da API Datasul.

---

# Segurança

Nunca armazenar credenciais.

Nunca armazenar tokens em variáveis globais.

Seguir estratégia definida pelo módulo de autenticação.

---

# Padrões Obrigatórios para Agentes de IA

Ao implementar qualquer funcionalidade, o agente deve:

* seguir esta arquitetura;
* utilizar componentes PO-UI;
* manter tipagem forte;
* evitar duplicação;
* criar componentes reutilizáveis;
* manter baixo acoplamento;
* manter alta coesão;
* seguir Clean Code;
* seguir SOLID quando aplicável;
* criar código pronto para produção.

---

# Checklist de Implementação

Antes de considerar uma funcionalidade concluída, verificar:

* Arquivos organizados corretamente.
* Componentes reutilizáveis.
* Nenhum uso de `any`.
* Services separados.
* Models criados.
* Interfaces criadas.
* Change Detection OnPush.
* Angular Signals quando aplicável.
* Componentes PO-UI utilizados.
* Responsividade para tablet validada.
* Tratamento de loading implementado.
* Tratamento de erros implementado.
* Código limpo e legível.
* Estrutura preparada para integração com a API Datasul.
