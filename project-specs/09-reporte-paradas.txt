# Reporte de Paradas

> Documento AI-First destinado aos agentes de código (Codex, BMAD, Claude Code e OpenCode).

---

# 1. Objetivo

A tela **Reporte de Paradas** é responsável pelo registro de interrupções ocorridas durante a execução de uma operação de produção.

Seu objetivo é permitir que o operador informe, de maneira rápida e padronizada, os motivos de parada ocorridos durante a fabricação, registrando o período da interrupção e demais informações necessárias para rastreabilidade da produção.

Esta tela deve operar como uma **janela modal (Floating Window)**, preservando o contexto da operação em andamento e retornando automaticamente para a tela chamadora após a conclusão da ação.

Todo o comportamento visual, identidade da aplicação, componentes PO-UI, padrões de layout e arquitetura devem seguir os documentos globais do projeto (`00-design-system.md` até `05-padroes-ui.md`).

---

# 2. Contexto de Negócio

Durante uma ordem de produção é comum ocorrerem interrupções por diversos motivos:

* Setup
* Almoço
* Reunião
* Troca de turno
* Manutenção
* Falta de material
* Limpeza
* Ajustes
* Outros motivos cadastrados no ERP

Essas interrupções impactam diretamente:

* Tempo produtivo
* Eficiência da máquina
* OEE
* Custos de fabricação
* Indicadores industriais
* Rastreabilidade da produção

O sistema deve permitir que essas ocorrências sejam registradas imediatamente durante a execução da operação, evitando perda de informações e garantindo a correta contabilização do tempo parado.

---

# 3. Papel da Tela no Fluxo Geral

A tela **não é acessada diretamente pelo menu principal**.

Ela somente pode ser aberta através do botão **Parada** existente nas telas:

* Reporte Operação (`08-reporte-operacao.md`)
* Reporte Batelada (`17-reporte-batelada.md`)

Fluxo simplificado:

```text
Centro de Trabalho
        │
        ▼
Reporte Operação
        │
        ├──────────────► Reporte Batelada
        │                       │
        │                       │
        └──── Botão Parada ◄────┘
                 │
                 ▼
        Reporte de Paradas
                 │
                 ▼
Retorna para a tela chamadora
```

A tela nunca deve alterar o fluxo principal da produção.

Ela funciona como uma operação auxiliar.

# 7. Componentes Identificados

## 7.1 Cabeçalho

Responsável por identificar a funcionalidade.

### Elementos

* Logo Cortag
* Título "Paradas"

### Componentes

```text
po-container

po-image

po-label
```

---

## 7.2 Pesquisa do Motivo

Permite localizar rapidamente um motivo de parada.

Visualmente comporta-se como um Lookup.

### Informações exibidas

Exemplo:

```text
01 - Setup
```

### Funcionalidades

* pesquisa por código
* pesquisa por descrição
* autocomplete
* seleção de item

### Componente sugerido

```text
po-lookup
```

ou

```text
po-combo
```

caso a lista seja pequena.

---

## 7.3 Botão Adicionar

Posicionado ao lado do lookup.

Representado apenas pelo símbolo **+**.

Função:

Adicionar o motivo selecionado na lista de paradas registradas.

Fluxo esperado:

```text
Selecionar motivo

↓

Adicionar

↓

Lista atualizada
```

---

## 7.4 Lista de Paradas

Representa todas as paradas registradas para o reporte atual.

Cada linha contém:

* Código
* Descrição
* Tempo

Exemplo:

| Código | Descrição   | Tempo    |
| ------ | ----------- | -------- |
| 02     | Almoço      | 01:00:00 |
| 05     | Reunião     | 00:10:00 |
| 15     | Troca Turno | 00:15:00 |

A lista deve permitir seleção de um item para edição de seus dados.

---

## 7.5 Formulário Temporal

Após selecionar um item da lista, o operador informa o período correspondente.

Campos identificados:

| Campo       | Tipo |
| ----------- | ---- |
| Data Início | Date |
| Hora Início | Time |
| Data Fim    | Date |
| Hora Fim    | Time |

Esses campos representam o intervalo de duração da parada.

---

## 7.6 Checkbox

Campo booleano.

Descrição:

```text
Parada Programada
```

Indica se aquela interrupção fazia parte do planejamento operacional ou ocorreu de forma inesperada.

---

## 7.7 Painel de Contexto

Área somente leitura contendo informações da operação atualmente reportada.

Campos identificados:

| Campo              | Editável |
| ------------------ | -------- |
| Centro de Trabalho | Não      |
| Grupo Máquina      | Não      |
| Operador / Equipe  | Não      |
| Turno              | Não      |

Esses dados possuem finalidade exclusivamente informativa para evitar registros em contexto incorreto.

---

## 7.8 Rodapé

O rodapé contém três ações principais.

### Voltar

Fecha a janela sem gravar alterações.

---

### Salvar

Valida as informações.

Persiste a parada.

Atualiza o reporte.

Retorna para a tela chamadora.

---

### Sair

Encerra o modal.

A ação exata dependerá das regras de negócio definidas pelo fluxo de produção e será detalhada na seção de regras funcionais.

# 10. Arquitetura da Implementação

A funcionalidade deverá ser implementada como uma **feature independente**, seguindo a arquitetura **Feature First** definida no projeto.

Esta tela deve ser reutilizável, podendo ser aberta tanto pelo fluxo de **Reporte Operação** quanto pelo fluxo de **Reporte Batelada**, sem duplicação de código.

Toda a lógica deve ser encapsulada na própria feature, recebendo apenas o contexto da produção (CT, Operação, Operador, Batelada, etc.) através de parâmetros de entrada.

# 17. Regras de UX

* A pesquisa deve possuir foco automático ao abrir a tela.
* O botão "+" somente poderá ser utilizado quando houver um motivo válido selecionado.
* Após adicionar um motivo, ele deve tornar-se automaticamente o item selecionado na lista.
* A mudança de seleção na lista deve atualizar imediatamente os campos do formulário.
* Os campos de data e hora devem utilizar máscaras apropriadas.
* O painel contextual deve permanecer sempre visível.
* O botão **Salvar** deve possuir maior destaque visual por representar a ação primária.
* Os botões **Voltar** e **Sair** devem ser tratados como ações secundárias.
* Toda operação de gravação deve fornecer feedback visual ao operador.
* A interface deve ser totalmente operável por toque, sem exigir precisão de mouse.

# 18. Regras de Negócio

## RN-01 — Abertura da Tela

A tela somente poderá ser aberta a partir das telas:

* Reporte Operação
* Reporte Batelada

Não deverá existir navegação direta pelo menu da aplicação.

---

## RN-02 — Contexto Obrigatório

Ao abrir a tela, deverá ser recebido o contexto da produção contendo, no mínimo:

* Centro de Trabalho
* Grupo Máquina
* Operação ou Batelada
* Operador ou Equipe
* Turno
* Identificador do Reporte

Caso essas informações não estejam disponíveis, a tela não deverá permitir o registro de uma parada.

---

## RN-03 — Cadastro do Motivo

Somente poderão ser registrados motivos de parada existentes no cadastro corporativo do ERP.

Não será permitido criar novos motivos nesta tela.

---

## RN-04 — Inclusão de Motivos

O botão **Adicionar (+)** somente poderá ser habilitado quando houver um motivo válido selecionado.

Após a inclusão:

* o motivo passa a compor a lista de paradas do reporte;
* torna-se automaticamente o item selecionado;
* o formulário é habilitado para preenchimento.

---

## RN-05 — Período da Parada

Cada parada deverá possuir um intervalo composto por:

* Data/Hora Inicial
* Data/Hora Final

Esses valores representam o período efetivo da interrupção.

---

## RN-06 — Duração

A duração da parada deverá ser calculada automaticamente.

```text
Duração = Data/Hora Final - Data/Hora Inicial
```

O operador nunca deverá informar a duração manualmente.

---

## RN-07 — Atualização da Lista

Após alterar qualquer informação de uma parada:

* a lista deverá ser atualizada;
* a duração exibida deverá ser recalculada;
* o item deverá permanecer selecionado.

---

## RN-08 — Parada Programada

O campo **Parada Programada** apenas classifica a ocorrência.

Ele não altera:

* duração;
* cálculo de tempo;
* fluxo da tela.

Seu impacto ocorrerá posteriormente em indicadores gerenciais e integrações com o ERP.

---

## RN-09 — Persistência

Ao salvar:

* todas as paradas deverão ser persistidas;
* deverão permanecer vinculadas ao reporte atual;
* deverão ser retornadas para a tela chamadora.

---

## RN-10 — Cancelamento

Selecionar **Voltar** fecha o modal.

Nenhuma alteração deverá ser persistida.

---

## RN-11 — Erros

Caso ocorra falha durante a gravação:

* o modal permanece aberto;
* os dados preenchidos devem ser preservados;
* deve ser apresentada mensagem amigável ao operador.

---

# 19. Validações

## Campos Obrigatórios

Obrigatórios:

* Motivo
* Data Inicial
* Hora Inicial

Quando a parada for encerrada:

* Data Final
* Hora Final

também passam a ser obrigatórios.

---

## Intervalo

Não permitir:

```text
Fim < Início
```

---

## Datas Futuras

Não permitir datas posteriores ao horário atual da produção, salvo se houver regra específica do ERP.

---

## Horários Inválidos

Não permitir:

* hora inexistente;
* datas inválidas;
* intervalos negativos.

---

## Motivo Duplicado

A aplicação poderá permitir múltiplos registros do mesmo motivo, desde que representem ocorrências distintas.

A validação dependerá das regras do ERP Datasul.

---

## Registro Vazio

Não permitir salvar quando nenhuma parada tiver sido adicionada.

---

# 25. Tratamento de Erros

A implementação deverá prever, no mínimo:

* falha de comunicação com a API;
* timeout;
* perda de conexão;
* motivo inexistente;
* registro removido durante a edição;
* conflito de concorrência;
* erro de autenticação;
* erro de autorização;
* erro interno do servidor.

Em qualquer uma dessas situações:

* manter os dados preenchidos;
* informar claramente o problema ao operador;
* permitir nova tentativa de gravação sem necessidade de redigitação.

# 26. Casos de Teste

## CT-01 — Abrir Tela

**Dado** que o operador esteja na tela de Reporte Operação ou Reporte Batelada

**Quando** pressionar o botão **Parada**

**Então** a janela de Reporte de Paradas deverá ser exibida carregando o contexto da produção.

---

## CT-02 — Pesquisar Motivo

**Dado** que existam motivos cadastrados

**Quando** o operador pesquisar por código ou descrição

**Então** deverão ser exibidos apenas os motivos compatíveis com a pesquisa.

---

## CT-03 — Adicionar Motivo

**Dado** um motivo selecionado

**Quando** clicar no botão **+**

**Então** o motivo deverá ser incluído na lista de paradas e automaticamente selecionado.

---

## CT-04 — Informar Período

**Dado** uma parada selecionada

**Quando** informar Data/Hora Inicial e Data/Hora Final

**Então** a duração deverá ser recalculada automaticamente.

---

## CT-05 — Salvar

**Dado** uma parada válida

**Quando** clicar em **Salvar**

**Então**

* os dados deverão ser persistidos;
* o modal deverá ser fechado;
* a tela chamadora deverá ser atualizada.

---

## CT-06 — Cancelar

**Quando** clicar em **Voltar**

**Então**

* nenhuma alteração deverá ser gravada;
* o modal deverá ser fechado.

---

## CT-07 — Falha de Comunicação

**Dado** indisponibilidade da API

**Quando** tentar salvar

**Então**

* exibir mensagem de erro;
* manter os dados preenchidos;
* permitir nova tentativa.

---

## CT-08 — Datas Inválidas

**Quando**

```text
Data/Hora Final < Data/Hora Inicial
```

**Então**

* impedir o salvamento;
* destacar os campos inválidos;
* informar o motivo da validação.

# 27. Critérios de Aceite

A funcionalidade será considerada concluída quando:

* A tela puder ser aberta pelos dois fluxos de reporte.
* Os motivos forem carregados corretamente.
* O operador puder pesquisar motivos.
* O botão **Adicionar** incluir novos registros.
* A lista permanecer sincronizada com o formulário.
* A duração for calculada automaticamente.
* O painel contextual refletir corretamente a produção ativa.

# 32. Considerações de Implementação

Toda a lógica referente às paradas deverá permanecer encapsulada nesta feature, permitindo futura reutilização em outros processos do sistema.

Também é recomendável que a implementação utilize formulários reativos (`Reactive Forms`) para facilitar validações, testes e manutenção.
