# 1. Objetivo

A tela **Centro de Trabalho** é responsável por estabelecer o contexto operacional da aplicação.

Ela identifica:

- qual Centro de Trabalho será utilizado;
- qual Operador está utilizando o sistema;
- qual será o modo de reporte utilizado durante a operação.

Após as validações necessárias, esta tela funciona como ponto de entrada para os módulos operacionais do sistema.

Os módulos acessíveis são:

- Reporte de Operação
- Reporte por Batelada
- Inspeção de Processo

Esta tela não possui finalidade de cadastro nem manutenção de informações.

Seu objetivo é apenas validar informações operacionais, carregar o contexto de trabalho e direcionar o usuário para o fluxo correto.

---

# 2. Contexto de Negócio

Na operação industrial da Cortag, um operador sempre executa atividades dentro de um determinado Centro de Trabalho.

Antes que qualquer produção seja apontada ou qualquer inspeção seja realizada, o sistema precisa conhecer:

- qual Centro de Trabalho está ativo;
- quem é o operador responsável;
- qual modalidade de reporte será utilizada.

Essas informações passam a representar o contexto operacional da sessão.

Todos os módulos posteriores assumem que esse contexto já foi previamente validado.

Portanto, esta tela funciona como um **Gateway Operacional** para todo o restante da aplicação.

---

# 3. Papel da Tela na Aplicação

Dentro do fluxo geral definido em `02-fluxo-geral.md`, esta tela representa a primeira etapa operacional após autenticação do usuário.

Fluxo simplificado:

```text
Login

↓

Menu Principal

↓

Centro de Trabalho

↓

Seleciona Centro

↓

Valida Operador

↓

Escolhe modo de Reporte

↓

┌─────────────────────────────┐
│ Reporte Operação            │
├─────────────────────────────┤
│ Reporte Batelada            │
├─────────────────────────────┤
│ Inspeção Processo           │
└─────────────────────────────┘
```

Sem um Centro de Trabalho válido, nenhum dos módulos operacionais poderá ser acessado.

---

# 4. Objetivos Funcionais

A tela deve permitir:

- localizar um Centro de Trabalho;
- exibir automaticamente seus dados;
- identificar o operador responsável;
- validar a identificação do operador;
- selecionar o modo de reporte;
- direcionar o usuário ao módulo correspondente.

## Botão Reporte

Responsabilidade:

Abrir o fluxo de reporte correspondente ao modo selecionado.

Comportamento:

Se:

```

```

Abrir:

```
Tela Reporte Operação
```

Se:

```
Reporte por = Batelada
```

Abrir:

```
Tela Reporte Batelada
```

Esta tela será documentada em documentos específicos.

---

## Botão Inspeção

Responsabilidade:

Abrir o módulo de Inspeção de Processo.

Destino:

```
Tela Inspeção Processo
```

Será documentada posteriormente.

---

## Botão Voltar

Estado atual:

Presente no protótipo.

Análise arquitetural:

Como a aplicação utiliza Menu Flutuante disponível em qualquer tela, este botão torna-se redundante.

Recomendação:

Marcar como **Depreciado**.

Sua implementação deverá depender de validação junto aos usuários da Cortag.

Caso removido, a navegação para o Menu Principal será realizada exclusivamente pelo Menu Flutuante.

# 9. Layout para Tablets

A tela foi desenhada considerando tablets utilizados em ambiente industrial.

Diretrizes:

- orientação vertical (Portrait);
- componentes centralizados;
- largura fixa para melhor ergonomia;
- áreas de toque seguindo o Design System;
- espaçamento amplo entre componentes;
- campos ocupando praticamente toda a largura disponível;
- botões inferiores de fácil acesso com uma única mão.

Não deverá existir rolagem vertical em condições normais de utilização.

Toda a interface deve permanecer visível em uma única tela.

---

# 10. Responsabilidade da Tela

A tela possui responsabilidade única:

**Construir e validar o contexto operacional antes da execução de qualquer operação produtiva.**

Ela **não** deverá:

- cadastrar informações;
- alterar dados do Centro de Trabalho;
- alterar Operadores;
- persistir configurações permanentes;
- executar reportes;
- executar inspeções.

Sua única responsabilidade é preparar o contexto necessário para os módulos subsequentes.

# 21. Regras de Negócio

## RN-001

O Centro de Trabalho deve existir.

Caso contrário:

Não permitir continuidade.

---

## RN-002

Os campos:

- Descrição
- Grupo Máquina
- Estab

Nunca poderão ser editados manualmente.

Sempre são provenientes da API.

---

## RN-003

O operador deve ser validado antes do acesso aos módulos.

---

## RN-004

Sem operador válido:

Reporte e Inspeção permanecem desabilitados.

---

## RN-005

O tipo de reporte define exclusivamente o destino do botão Reporte.

```
Operador

↓

Tela Reporte Operação
```

```
Batelada

↓

Tela Reporte Batelada
```

---

## RN-006

Inspeção ignora o tipo de reporte.

Sempre abre:

```
Tela Inspeção Processo
```

---

## RN-007

O contexto operacional deve permanecer disponível enquanto durar a sessão do usuário.

---

## RN-008

Ao alterar o Centro de Trabalho, o contexto operacional anterior deve ser descartado.

Isso inclui:

- Operador
- Nome
- Validade
- Tipo de reporte
- Dados temporários associados ao contexto anterior

---

## RN-009

Ao alterar o Operador, apenas os dados do operador devem ser atualizados.

As informações do Centro de Trabalho permanecem inalteradas.

---

# 22. Regras de UX

A tela deve minimizar a quantidade de interações necessárias.

Diretrizes:

- foco automático no campo **Código** ao abrir a tela;
- após validar o Centro de Trabalho, mover automaticamente o foco para **Operador**;
- após validar o Operador, mover o foco para **Validade**;
- utilizar teclado numérico sempre que possível para campos numéricos;
- exibir feedback visual imediato durante validações;
- evitar mensagens modais para erros simples, priorizando mensagens inline conforme definido em `05-padroes-ui.md`;
- manter os botões **Reporte** e **Inspeção** visíveis durante toda a operação;
- preservar o estado da tela durante pequenas oscilações de rede, evitando perda dos dados já informados.

# 34. Loading

Durante qualquer consulta:

- impedir múltiplos cliques;
- bloquear apenas os controles envolvidos na operação;
- manter os dados já carregados visíveis;
- exibir indicador de carregamento discreto conforme definido no Design System.

Evitar recarregamento completo da página.

---

# 35. Performance

A tela deve responder de forma praticamente instantânea.

Requisitos:

- inicialização inferior a 500 ms (sem chamadas de API);
- atualização imediata dos campos locais;
- consultas assíncronas sem bloquear a interface;
- reutilização do contexto operacional durante a sessão.

---

# 36. Acessibilidade

Embora destinada a tablets industriais, a tela deve seguir as diretrizes de acessibilidade adotadas pelo projeto:

- navegação por teclado quando disponível;
- labels associadas aos campos;
- foco visível;
- contraste conforme o Design System;
- mensagens de erro legíveis;
- áreas de toque compatíveis com operação por luvas, conforme especificado em `05-padroes-ui.md`.

---

# 37. Observações para Implementação

- Os ícones de câmera representam uma funcionalidade futura de leitura por código de barras ou QR Code e devem ser implementados inicialmente apenas como botões desabilitados ou placeholders, conforme decisão do projeto.
- O **Contexto Operacional** deve ser tratado como uma entidade de aplicação, sendo compartilhado entre todas as telas subsequentes.
- Nenhuma informação operacional deve ser persistida localmente após o encerramento da sessão.
- A tela deve permanecer desacoplada das regras específicas de Reporte e Inspeção, atuando apenas como ponto de preparação do contexto e navegação.
- Toda a lógica de negócio deve residir nos Services, mantendo os componentes focados na apresentação e interação com o usuário.

# 38. Critérios de Aceite

A implementação da tela será considerada concluída quando atender aos critérios abaixo.

---

## CAT-001 — Inicialização

**Dado** que o usuário acessou a tela

**Então**

- a tela deve abrir sem erros;
- o foco inicial deve estar no campo **Código**;
- todos os campos devem iniciar vazios;
- os botões **Reporte** e **Inspeção** devem permanecer desabilitados.

---

## CAT-002 — Consulta do Centro de Trabalho

**Dado** que o usuário informou um código válido

**Então**

o sistema deve preencher automaticamente:

- Descrição;
- Grupo Máquina;
- Estabelecimento.

# 44. Considerações Arquiteturais

A tela **Centro de Trabalho** é o ponto de criação do **Contexto Operacional** da aplicação.

Todas as telas subsequentes deverão assumir que esse contexto já existe e foi previamente validado.

Por esse motivo, esta Feature deve ser considerada uma **Feature Base** do sistema, servindo como pré-requisito para todos os fluxos operacionais de produção e inspeção.

Ela deve permanecer pequena, objetiva e altamente desacoplada, concentrando-se apenas em:

- identificação do Centro de Trabalho;
- identificação do Operador;
- seleção do modo de reporte;
- criação do Contexto Operacional;
- navegação para os módulos funcionais.

Qualquer lógica relacionada ao processo produtivo, apontamentos, inspeções ou regras específicas deve permanecer exclusivamente nas respectivas Features.
