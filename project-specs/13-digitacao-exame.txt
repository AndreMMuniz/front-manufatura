# 1. Objetivo

A tela **Digitação de Exame** é responsável pela execução operacional de uma inspeção de qualidade.

Nela o operador realiza a coleta e registro dos valores medidos para cada característica definida no roteiro de inspeção gerado anteriormente.

Esta tela representa a etapa onde os dados deixam de ser apenas um roteiro planejado e passam a constituir registros efetivos de controle da qualidade.

Seu principal objetivo é garantir que todas as medições sejam realizadas de maneira padronizada, validando automaticamente os valores digitados contra as tolerâncias especificadas para cada característica.

---

# 2. Contexto de Negócio

Esta tela é aberta a partir da tela **Inspeção de Processo** quando existe um exame pendente de execução.

Fluxo simplificado:

```text
Centro de Trabalho
        ↓
Inspeção de Processo
        ↓
Selecionar Exame
        ↓
Digitação de Exame
```

Durante esta etapa o operador deverá:

* visualizar os dados do exame;
* visualizar a característica atual;
* consultar os valores de referência;
* informar os valores medidos;
* registrar observações quando necessário;
* navegar entre as características do roteiro;
* salvar as medições;
* concluir o exame.

Todo o processo deve ocorrer de forma rápida, minimizando o número de toques na tela devido ao ambiente industrial onde será utilizado.

---

# 3. Objetivos Funcionais

A tela deverá permitir:

* carregar um exame previamente gerado;
* apresentar os dados gerais do exame;
* apresentar a característica atualmente em inspeção;
* exibir limites de referência;
* receber valores medidos;
* validar automaticamente os valores digitados;
* impedir inconsistências básicas de preenchimento;
* permitir navegação entre características;
* registrar observações;
* salvar parcialmente a inspeção;
* finalizar o exame após todas as características serem preenchidas.

---

# 6. Estrutura Visual

A tela é dividida em cinco regiões principais.

## 6.1 Cabeçalho

Responsável apenas pela identificação da funcionalidade.

Componentes:

* Logo Cortag
* Título da tela

Não possui toolbar.

Segue integralmente o padrão definido em `05-padroes-ui.md`.

---

## 6.2 Identificação do Exame

Primeiro bloco abaixo do cabeçalho.

Exibe o exame atualmente em execução.

Campos previstos:

| Campo | Tipo    | Editável |
| ----- | ------- | -------- |
| Exame | Display | Não      |

O identificador deverá ser recebido da tela anterior.

---

## 6.3 Painel de Informações

Bloco cinza contendo informações gerais do exame.

Todos os campos são somente leitura.

Campos identificados:

| Campo      | Tipo    |
| ---------- | ------- |
| Código     | Display |
| Descrição  | Display |
| Versão     | Display |
| Frequência | Display |
| Unidade    | Display |
| NQ         | Display |
| Nível      | Display |

Este painel serve apenas como contexto para o operador durante toda a execução do exame.

---

## 6.4 Área da Característica

Representa a principal área de trabalho da tela.

Cada característica do roteiro será apresentada individualmente.

Componentes:

* Código da característica
* Nome da característica
* Descrição técnica
* Tolerância nominal

Exemplo observado:

```text
010

Cota 488,0 +/- 3,0 mm
```

Apenas uma característica permanece ativa por vez.

---

## 6.5 Área de Digitação

Responsável pela entrada dos resultados medidos.

Campos identificados:

| Campo      | Tipo     | Obrigatório |
| ---------- | -------- | ----------- |
| Referência | Display  | Sim         |
| Min        | Numérico | Sim         |
| Max        | Numérico | Sim         |
| Observação | Texto    | Não         |

A referência é informativa e não pode ser alterada pelo operador.

---

## 6.6 Navegação

Na parte inferior da área de inspeção existem controles para navegação entre características.

Componentes:

* Anterior
* Próxima

Esses controles permitem percorrer todas as características do roteiro mantendo o estado da inspeção.

---

## 6.7 Barra de Progresso

Foi identificada uma barra vertical localizada na lateral direita da tela.

Ela deverá ser documentada como um indicador visual de progresso da inspeção.

Funções esperadas:

* indicar avanço da inspeção;
* indicar posição atual dentro do roteiro;
* fornecer feedback visual contínuo ao operador.

A implementação poderá evoluir conforme a definição da API, mantendo esta responsabilidade funcional.

---

## 6.8 Rodapé de Ações

Botões identificados:

| Botão  | Função                                            |
| ------ | ------------------------------------------------- |
| Salvar | Persiste os dados da característica atual         |
| Voltar | Retorna para a tela anterior                      |
| Sair   | Abandona a inspeção retornando ao fluxo principal |

A disposição deverá seguir o padrão de navegação definido em `05-padroes-ui.md`.

# 10. Estados da Tela

## Loading

Exibido enquanto o exame é carregado.

```text
Abrindo exame...
```

---

## Ready

Estado padrão.

Todos os dados carregados.

Campos habilitados.

---

## Editing

Usuário preenchendo valores.

Campos editáveis.

Botão Salvar habilitado.

---

## Saving

Após clicar em Salvar.

Durante este estado:

* bloquear edição;
* exibir indicador visual;
* impedir múltiplos envios.

---

## Validation Error

Erro de preenchimento.

Exemplos:

* campo vazio;
* valor inválido;
* Min maior que Max;
* formato incorreto.

A navegação permanece bloqueada até correção.

---

## Out Of Range

Estado identificado na interface.

É exibido quando os valores informados ultrapassam os limites permitidos da característica.

Mensagem apresentada:

```text
Erro

Valores fora da variação permitida
```

A implementação deverá permitir que a aplicação trate este cenário de forma explícita, sem gerar falhas inesperadas.

---

## API Error

Falha de comunicação.

Exemplos:

* timeout;
* erro interno;
* perda de conexão.

A tela deverá permanecer consistente permitindo nova tentativa.

---

## Completed

Última característica concluída.

Estado utilizado para iniciar o fluxo de encerramento do exame.

---

# 13. Regras de Negócio

## RN-001 - Carregamento do Exame

A tela somente poderá ser aberta quando existir um exame válido selecionado na tela **Inspeção de Processo**.

Caso o exame não exista ou tenha sido removido, a aplicação deverá impedir a abertura da tela e retornar ao fluxo anterior.

---

## RN-002 - Exibição de uma Característica por Vez

Cada exame é composto por uma ou mais características de inspeção.

A interface deverá apresentar apenas uma característica por vez, reduzindo a quantidade de informações simultâneas e facilitando a operação em tablets industriais.

---

## RN-003 - Ordem Sequencial

As características deverão ser apresentadas exatamente na sequência definida pelo roteiro recebido da API.

A aplicação não poderá alterar a ordem de execução.

---

## RN-004 - Informações Somente Leitura

Os seguintes campos possuem caráter exclusivamente informativo:

* Código do exame
* Descrição
* Versão
* Frequência
* Unidade
* NQ
* Nível
* Código da característica
* Descrição
* Referência

Nenhum desses valores poderá ser alterado pelo operador.

---

## RN-005 - Valores Medidos

Cada característica poderá exigir uma ou mais medições.

Na interface identificada atualmente existem os campos:

* Min
* Max

Ambos deverão aceitar apenas valores numéricos.

---

## RN-006 - Observação

O campo **Observação** é opcional.

Sua finalidade é registrar informações complementares relevantes para a inspeção, tais como:

* condições do material;
* comportamento da medição;
* justificativas;
* anotações do operador.

---

## RN-007 - Salvamento

Ao acionar o botão **Salvar**, a aplicação deverá persistir os dados informados para a característica atualmente exibida.

O salvamento deverá ocorrer sem perda das medições já realizadas nas demais características.

---

## RN-008 - Navegação

Ao navegar entre características:

* os dados já digitados deverão permanecer carregados;
* os campos deverão ser restaurados automaticamente;
* nenhuma informação poderá ser perdida.

---

## RN-009 - Persistência Parcial

A aplicação deverá permitir que um exame permaneça parcialmente preenchido.

Caso o operador saia da tela e retorne posteriormente, as medições previamente salvas deverão ser recuperadas pela API.

---

## RN-010 - Conclusão

O exame somente poderá ser considerado concluído quando todas as características obrigatórias estiverem preenchidas.

---

# 14. Regras de Validação

## RV-001

Os campos **Min** e **Max** são obrigatórios.

Caso estejam vazios, o salvamento deverá ser bloqueado.

---

## RV-002

Somente números deverão ser aceitos.

Caracteres inválidos deverão ser rejeitados imediatamente.

---

## RV-003

Os campos deverão aceitar valores decimais conforme configuração da característica.

Exemplo:

```text
485
485.2
485.25
```

A quantidade de casas decimais poderá ser parametrizada futuramente pela API.

---

## RV-004

Caso ambos os campos estejam preenchidos:

```text
Min <= Max
```

Caso contrário:

```text
Min > Max
```

o sistema deverá impedir o salvamento e apresentar mensagem ao operador.

---

## RV-005

Os valores deverão ser comparados com os limites definidos para a característica.

Exemplo observado:

```text
Referência

485 - 491
```

A validação deverá ocorrer automaticamente após o preenchimento.

---

## RV-006

Caso a API informe novos critérios de aceitação (nominal, tolerância, desvio, percentual etc.), a camada de validação deverá ser extensível sem necessidade de alterar a interface.

---

# 15. Tratamento de Valores Fora da Tolerância

Foi identificado um estado específico da tela destinado à apresentação de falhas de inspeção.

Mensagem apresentada no mockup:

```text
Erro

Valores fora da variação permitida
```

Este estado deverá ser tratado como parte oficial do fluxo funcional.

Fluxo esperado:

```mermaid
flowchart TD

A[Operador informa valores]

A --> B[Validação automática]

B --> C{Dentro da tolerância?}

C -->|Sim| D[Salvar]

C -->|Não| E[Exibir estado de erro]
```

---

## Comportamento esperado

Ao detectar valores fora da faixa permitida:

* interromper o fluxo normal de salvamento;
* destacar visualmente o erro;
* informar claramente o motivo da rejeição;
* preservar os valores digitados;
* permitir nova tentativa após correção.

A lógica definitiva dependerá das regras disponibilizadas pelo Datasul, porém a arquitetura deverá prever esse cenário desde o início.

---

# 16. Navegação

## Botão Anterior

Responsável por retornar para a característica imediatamente anterior.

Caso a característica atual seja a primeira:

* botão desabilitado.

---

## Botão Próximo

Responsável por avançar para a próxima característica.

Caso seja a última:

* botão desabilitado;
* ou substituído pelo fluxo de conclusão (dependendo da regra da API).

---

## Botão Salvar

Fluxo esperado:

```text
Validar

↓

Persistir

↓

Atualizar progresso

↓

Liberar edição
```

---

## Botão Voltar

Retorna para a tela **Inspeção de Processo**.

Caso existam alterações não salvas, a aplicação deverá solicitar confirmação antes de abandonar a inspeção.

---

## Botão Sair

Encerra a execução da tela retornando ao fluxo principal da aplicação.

Também deverá solicitar confirmação quando houver alterações pendentes.

---

# 17. Regras de UX

A interface deverá seguir os princípios definidos em `05-padroes-ui.md`, observando ainda as seguintes diretrizes específicas.

## Operação por toque

Todos os elementos clicáveis deverão possuir área mínima compatível com uso em tablets industriais.

---

## Digitação rápida

Os campos numéricos deverão abrir preferencialmente o teclado numérico do dispositivo.

---

## Feedback imediato

Toda validação deverá ocorrer imediatamente após o preenchimento do campo, evitando erros apenas no momento do salvamento.

---

## Continuidade da operação

Sempre que possível, o operador deverá permanecer na mesma tela durante toda a execução do exame, evitando navegações desnecessárias.

---

## Clareza visual

As informações mais importantes devem possuir maior destaque visual:

1. Característica atual;
2. Faixa de referência;
3. Campos de medição;
4. Estado de aprovação ou erro.

---

## Robustez

Falhas de comunicação com a API não deverão ocasionar perda das medições já registradas.

O operador deverá ser capaz de retomar a inspeção após a normalização da comunicação.

# 18. Integração com API (Datasul)

As operações previstas são:

* Carregar exame

# 23. Responsabilidades das Camadas

## Page

Responsável apenas por:

* montar a interface;
* encaminhar eventos para a Facade;
* consumir Observables.

Não deverá conter regras de negócio.

---

## Facade

Responsável por:

* controlar o estado da tela;
* coordenar navegação;
* validar fluxo operacional;
* controlar loading;
* controlar progresso;
* integrar componentes.

Toda a lógica de apresentação deverá permanecer aqui.

---

## Service

Responsável por:

* comunicação com API;
* tratamento de erros HTTP;
* transformação de DTOs;
* persistência dos dados.

Não deverá conhecer componentes visuais.

---

## Components

Responsáveis apenas pela renderização e captura de eventos do usuário.

Toda regra de negócio deverá permanecer desacoplada.

---

## Models

Representam o domínio da aplicação.

Devem permanecer independentes dos contratos HTTP.

---

## DTOs

Representam exclusivamente os contratos de comunicação com a API.

Nunca deverão ser utilizados diretamente pela interface da aplicação.

---

# 24. Considerações de Extensibilidade

A arquitetura deverá permitir futuras evoluções sem necessidade de refatoração significativa.

Entre elas:

* características com apenas uma medição;
* características com múltiplas medições;
* medições qualitativas (Sim/Não);
* medições por seleção;
* captura automática por dispositivos de medição;
* leitura via código de barras ou QR Code;
* integração com instrumentos digitais;
* anexos (foto da peça);
* assinatura eletrônica do inspetor;
* validação em tempo real pelo Datasul.

A implementação inicial deverá manter esses pontos desacoplados, garantindo evolução futura da funcionalidade sem impacto estrutural.

# 25. Critérios de Aceite

A implementação da tela será considerada concluída quando atender aos critérios abaixo.

## Interface

* [ ] A tela segue integralmente o Design System definido no projeto.
* [ ] O layout está otimizado para tablets industriais.

* [ ] Os botões permanecem sempre acessíveis ao operador.

## Carregamento

* [ ] O exame é carregado corretamente a partir da tela anterior.
* [ ] Todas as informações do exame são exibidas.
* [ ] A primeira característica é apresentada automaticamente.
* [ ] O indicador de progresso é inicializado corretamente.

---

## Digitação

* [ ] O operador consegue informar valores mínimos.
* [ ] O operador consegue informar valores máximos.

* [ ] Os dados permanecem na tela após navegação entre características.

* [ ] Campos obrigatórios são validados.
* [ ] Apenas valores numéricos são aceitos.

* [ ] Valores fora da tolerância são tratados conforme regra de negócio.

* [ ] As medições são gravadas corretamente.
* [ ] Não ocorre perda de dados.

# 26. Casos de Teste

## Cenário 01

**Objetivo**

Abrir um exame válido.

**Resultado esperado**

Todas as informações do exame são carregadas corretamente.

---

## Cenário 02

**Objetivo**

Salvar uma característica preenchida corretamente.

**Resultado esperado**

A medição é persistida e permanece disponível ao retornar para a característica.

---

## Cenário 03

**Objetivo**

Tentar salvar campos vazios.

**Resultado esperado**

O sistema bloqueia o salvamento e apresenta mensagens de validação.

---

## Cenário 04

**Objetivo**

Informar caracteres não numéricos.

**Resultado esperado**

O sistema impede a digitação ou apresenta erro de validação.

---

## Cenário 05

**Objetivo**

Informar valor mínimo maior que o valor máximo.

**Resultado esperado**

O salvamento é bloqueado.

---

## Cenário 06

**Objetivo**

Informar valores fora da faixa permitida.

**Resultado esperado**

A interface apresenta o estado de erro **"Valores fora da variação permitida"**, preservando os valores digitados para correção ou tratamento conforme regra de negócio.

---

## Cenário 07

**Objetivo**

Navegar entre características.

**Resultado esperado**

As medições previamente registradas permanecem carregadas.

---

## Cenário 08

**Objetivo**

Interromper a inspeção após salvar parcialmente.

**Resultado esperado**

Ao retornar ao exame, a API recupera todas as medições já persistidas.

---

## Cenário 09

**Objetivo**

Finalizar um exame completo.

**Resultado esperado**

O sistema altera o status do exame para concluído e retorna ao fluxo de inspeção.

---

## Cenário 10

**Objetivo**

Simular indisponibilidade da API durante o salvamento.

**Resultado esperado**

A interface informa o erro, mantém os dados preenchidos e permite nova tentativa após a recuperação da comunicação.
